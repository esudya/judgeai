# Поиск прецедентов: перенос логики из jobbytime-matcher

Источник идей — сервис матчинга резюме и вакансий `jobbytime.com-group/jobbytime-matcher` (ветка `main`, прочитан 28.10.2026). Код **не копируется**: переносятся архитектурные решения, а реализация пишется заново под русский правовой текст, слои Clean Architecture и правило 0 AUTORUN (все данные — из БД с происхождением).

Задача в judgeAI: по проекту приговора найти похожие приговоры (прецеденты) и показать судье, где назначенное наказание находится в распределении практики, с объяснением по каждому совпадению.

## 1. Соответствие сущностей

| jobbytime-matcher | judgeAI |
|---|---|
| вакансия | приговор-прецедент (карточка `PrecedentCard`) |
| резюме | проект приговора (запрос) |
| секции описания (ROLE / REQUIREMENTS / …) | части приговора: вводная / описательно-мотивировочная / резолютивная |
| роль (job title) | квалификация: статья, часть, пункт УК по каждому эпизоду |
| навыки с уровнями required / preferred / … | обстоятельства: смягчающие и отягчающие (ст. 61, 63), с нормой |
| seniority / опыт | личность: судимости, рецидив (ст. 18), возраст |
| hard-фильтры (location, salary, …) | статья и часть, категория (ст. 15), рецидив, особый порядок, регион, период |
| score_breakdown | объяснение совпадения по осям + цитаты |
| — (нет аналога) | **распределение назначенных наказаний и позиция проекта в нём** |

## 2. Что переносим (с образцом в исходном проекте)

1. **Вектор ищет смысл, факты идут в фильтры и оси** (`build_embedding_text`). В эмбеддинг попадает только обезличенная фабула эпизода. Суд, регион, даты, ФИО, номера статей в вектор не кладём: их проверяют фильтры и оси. Правило закрепляется сигнатурой функции, которая просто не принимает эти поля.
2. **Разбор на части без LLM** (`description_sections.py::split_description`). Границы — по заголовкам «УСТАНОВИЛ», «ПРИГОВОРИЛ», в том числе вразрядку. Неопознанный фрагмент присоединяется к предыдущей части, а не выбрасывается.
3. **Извлечение «regex сначала, LLM только по окнам»** (`windows.py`, `salary_extractor.py`). Срок, вид и размер наказания ищутся regex в резолютивной части. В LLM уходит только окно ±150–300 символов вокруг неоднозначного места. Ответ кэшируется по sha256 окна и версии промпта. Это убирает проблему обрезки на 30 000 символов.
4. **Реестр экстракторов с происхождением** (`extraction/extractor.py`). Каждое поле: значение, метод (`regex` / `llm` / `none`), цитата, версия экстрактора, хэш входа. Ключ идемпотентности: `(поле, версия экстрактора, sha256 входа)`.
5. **Трёхзначные фильтры с причиной и настраиваемым действием** (`matching_hard_filters.py`, `hard_filter_states.py`). Результат `passed / failed / uncertain` + причина. Действие `exclude / score / info` задаётся конфигом. «Нет данных» — это `uncertain`, а не провал.
6. **Предфильтр внутри векторного запроса и точный скан вместо HNSW** (`pgvector_store.py::_search_by_vector`). Фильтр «та же статья и часть» стоит до `LIMIT`. HNSW с таким фильтром обрезает выдачу, а точный скан на десятках тысяч карточек укладывается в десятки миллисекунд.
7. **Несколько каналов поиска и слияние RRF** (`channel_store.py`, `rank_fusion.py`, `1/(60+rank)`). Каналы: вектор фабулы; квалификация (точное совпадение статьи и части); полнотекст PostgreSQL `tsvector` по ключевым признакам (в исходном проекте BM25 только в ТЗ, у нас он нужен для формулировок вроде «с незаконным проникновением в жилище»).
8. **Скоринг взвешенной суммой применимых осей** (`score_formula.py::score_v2`, `matching_axis_scoring.weighted_score`). Оси без данных выбрасываются, веса перенормируются. Потолки: например, другая часть статьи — оценка не выше заданного порога. Разложение по осям сохраняется в JSONB и служит объяснением.
9. **Покрытие обстоятельств с весами уровней** (`level_aware_skills_score`). Совпало ли признание, явка с повинной, возмещение ущерба, рецидив; у отягчающих и п. «и», «к» ч. 1 ст. 61 вес выше, так как они меняют пределы наказания.
10. **Экономия и надёжность**: вектор по хэшу текста (одинаковые фабулы делят вектор), журнал шагов импорта, advisory lock на прогон, учёт стоимости вызовов LLM.
11. **Методика оценки качества** (`formula_benchmark.py`, `benchmarks/synthetic-100/JUDGE.md`). Набор запросов, разметка релевантности 0/1/2 (LLM-судья плюс выборочная проверка юристом и второй разметчик с κ), AUC по запросу, доля релевантных в топ-10, парный бутстрэп как условие слияния MR, меняющего формулу.

## 3. Что не переносим или делаем заново

- Словари на английском (навыки, роли, regex экстракторов). Вместо них: рубрикатор статей УК из нашей БД (`legal_provisions`, `criminal_article_sanctions`) и словарь обстоятельств по ст. 61 и 63.
- Константы и пороги под продукт вакансий, квоты, подписки, парсеры ATS.
- Внешние платные модели как обязательная часть. Эмбеддинги и реранкер выбираются по T19 (лицензии) и T17 (данные не уходят наружу); качество на русском юридическом тексте меряется нашим бенчмарком.
- **Новое, чего в исходном проекте нет:** статистика наказаний по найденным прецедентам (медиана, перцентили, доля условных, применение ст. 64 и 73) и положение проекта в этом распределении. Считается кодом, не моделью.

## 4. Целевая архитектура в judgeAI

```
legal_core (domain, без фреймворков)
  PrecedentCard, Episode, Circumstance, ImposedSentence
  rules: hard_filters (tri-state), score_axes, punishment_distribution
application (use cases)
  ExtractVerdictCard, IndexPrecedent, FindSimilarPrecedents, CompareWithPractice
adapters
  verdict_segmenter, punishment_extractor (regex + окна LLM), circumstance_extractor,
  embedding_text_builder, embedding_provider (fastembed), reranker (опционально)
infrastructure
  pgvector store (точный скан + предфильтр), tsvector, Alembic-миграции, CLI импорта
```

Хранение: `precedent_cards` (структура + происхождение: URL, дата загрузки, sha256), `precedent_card_fields` (значение, метод, цитата, версия экстрактора, хэш входа), `precedent_embeddings` (модель, хэш текста, вектор), `precedent_matches` (запрос, кандидат, оценка, разложение JSONB). Каждая таблица — отдельной миграцией с downgrade.

## 6. Риски

- Без реального корпуса (T6) всё, кроме T24, проверяется только на синтетике.
- Обезличивание прецедентов до эмбеддинга обязательно (T17): в векторе и карточке не должно быть ФИО и адресов.
- Похожесть по тексту не равна юридической сопоставимости: решает фильтр по статье и части и ось обстоятельств, вектор только упорядочивает внутри.
